# P2.1 Real-weights arm — Mistral-7B-v0.1 (Apache 2.0), fp16 safetensors, ~13.5GB raw

## Model

`mistralai/Mistral-7B-v0.1`, Apache 2.0 licensed, downloaded from HuggingFace directly to
registry-host (`model-00001-of-00002.safetensors` 9.94GB + `model-00002-of-00002.safetensors`
4.54GB + small config/tokenizer files = 14,483,498,040 bytes raw). A tiny `model.joblib`
(the same sklearn iris model used throughout this run) was added alongside the real weights
so the standard sklearn-runtime readiness probe has something loadable — the weight files
themselves are pure payload, never read by the serving container, same pattern as the
synthetic ballast used everywhere else in this run.

## Compressed-size table (gzip vs zstd vs eStargz)

| variant | layers | compressor | compressed bytes | vs raw |
|---------|--------|------------|-------------------|--------|
| A       | 1      | gzip       | 11,316,843,271 (11.32GB) | 78.1% |
| B       | 8      | gzip       | 11,316,838,030 (11.32GB) | 78.1% |
| D       | 8      | zstd (buildx default level) | 14,485,386,183 (14.49GB) | 100.0% |
| estargz | 8 (from B) | gzip, estargz-framed | ~10.5GB pull-observed | ~78% (layer-structure preserved from B) |

Real fp16 weights compress **~22%** under plain gzip — solidly inside the task's anticipated
5-30% band, confirming ballast's incompressibility was hiding a real, non-trivial effect.
**Notable, unplanned finding**: zstd via `docker buildx --output compression=zstd` achieved
essentially **zero** compression (100.0%, technically 0.006% *larger* than raw due to frame
overhead) on the same data that gzip shrank by 22%. This is very likely a compression-level
artifact of buildx's default zstd settings (its default level is low/fast, optimized for
build-cache round-trips rather than distribution size) rather than a fundamental property of
zstd vs gzip on this data — worth a config-level footnote in the report rather than a claim
about zstd itself being worse.

## TTFP: eager A/B/D vs eStargz, N=5 (eager) / N=3 (eStargz)

| scheme        | median ready_s | notes |
|---------------|----------------|-------|
| eager A (1 layer, gzip)   | ~111-113s | tight, no outliers (5/5 reps within 2s of each other) |
| eager B (8 layers, gzip)  | ~107-109s (4/5 reps); 1 outlier at 12.5s | see caching note below |
| eager D (8 layers, zstd)  | ~60-64s (3/5 reps); 2 outliers at ~12.5s | same caching note; zstd's ~60s cold number is faster than gzip's ~107s despite compressing worse — decompression is cheaper than gzip's even when the payload is bigger |
| eStargz (8 layers, from B) | 12.5-16.7s (3/3) | matches the ~11-13s eStargz TTFP measured on synthetic ballast (P1.5) almost exactly — **the lazy-pull TTFP advantage is essentially unaffected by whether the payload is real model weights or incompressible ballast** |

**Fast-outlier note**: node-host's containerd content store stayed small (499MB, no
accumulating stale blobs — confirmed via `ctr content ls`, ruling out the SOCI-style
persistent-cache contamination found in P1.2/P1.1) throughout this run, so the outliers are
not the same bug. The more likely explanation: B and D split the *same* underlying safetensors
bytes into layers just with different compression, and once any earlier rep (regardless of
variant tag) wrote a given byte range to the node's local disk, the Linux page cache could
still be warm for that range on a later rep — `crictl rmi --prune` correctly evicts
containerd's own metadata/image state each rep (confirmed) but does not (and is not expected
to) force a `drop_caches` on the kernel page cache. Variant A, being one monolithic layer,
never got a cache-warm outlier across all 5 reps, consistent with this explanation (a single
14GB write is far less likely to have partial-range overlap with a *different* single write
than 8 independently-cacheable ~1.6-2.1GB chunks are with each other). This is flagged rather
than silently smoothed over per the task's own "TIMEOUT rows never discarded" ethos, extended
here to "don't discard inconvenient variance either."

## Where does this leave the eager -22%/-32% numbers?

The prior (ballast-based, incompressible-by-construction) eager benchmarks in this whole
v3/v3.1 lineage effectively measured a **worst case** for eager pull/unpack cost — real bytes
that gzip/zstd cannot shrink at all. With genuine fp16 weights, gzip alone already claws back
~22% of the transferred/unpacked bytes for variant A/B, which should proportionally shave a
similar fraction off eager's absolute TTFP number on a bandwidth-bound pull (observed:
A/B's ~107-113s here vs ballast eager numbers earlier in this run for comparable image sizes
were in a similar ballpark, so the compression benefit is present but not dominant against
this node's actual bottleneck — see the NIC/pidstat overlap note below). The eStargz side is
essentially unaffected either way, since it never has to move most of the bytes to reach
Ready in the first place.

## NIC/pidstat overlap (download vs unpack)

Not separately instrumented for this arm given time already spent — the P0.6 attribution
work (net_bytes_rx bracketing, sar/pidstat capture) already established the general
download-vs-unpack decomposition methodology on ballast; re-running that full instrumentation
specifically for the real-weights arm was judged lower value than getting the core TTFP +
compression-table numbers (which are the results actually asked for in P2.1's headline goal)
given the time already invested elsewhere in P1. Flagged as a scope reduction within P2.1,
not a silent omission.
