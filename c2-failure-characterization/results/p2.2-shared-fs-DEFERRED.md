# P2.2 shared-fs ENOSPC repeat — deferred, argued via evidence instead of a new live measurement

## What was asked

Repeat the ENOSPC experiment with the stargz cache on the SAME filesystem kubelet sees as
`imageFs`, stock eviction thresholds, to answer: is there a window where lazy reads fail
*before* kubelet's own DiskPressure/eviction machinery gets a chance to intervene?

## Why this was not attempted live in this run

Every dedicated-cache-root switch attempted earlier in this v3.1 run (the abandoned dual
cache-root approach in `01-cluster-up.sh`/`05-setup-stargz.sh`, and the SOCI equivalent in
P1.1) either silently corrupted containerd's snapshot state or broke live pod mounts —
because `snapshotter = "stargz"` (and later `"soci"`) is the **node-wide default**, every
currently-running system pod (etcd, kube-apiserver, coredns, kube-proxy, the KServe
controller) is *also* mounted through whichever daemon instance/root is currently active.
Restarting that daemon against a different root has, twice in this session, either left
those pods' live mounts unable to survive (P0.3's own finding: a stargz-grpc restart under a
live pod produces an unrecoverable Stale file handle) or corrupted containerd's snapshot
metadata badly enough to require a full cluster recreate (the P0.5 incident). Given P2.2 is
the last, explicitly most-cuttable item in the entire task ("if cutting, cut from the tail:
P2 → P1.3 → P1.2; P0 is never cut"), and the cluster is still needed intact for the
run's calibration-END step and final evidence collection, repeating that risk for one more
data point was judged not worth it — especially since the task's own text pre-authorizes
exactly this fallback: *"если не укладывается в таймбокс — аргументировать через паттерн
dedicated-volume в статье вместо этого, но реальное измерение сильнее слов."*

## The argument, backed by evidence already collected in this run

Every real ENOSPC induction actually run in v3.1 (P0.1's cumulative fill + 5s sampler,
P0.3's mechanism/recovery matrix, all ten reps of P0.5's pressure matrix) used the
**dedicated** `/cache-part` partition — deliberately *not* part of what kubelet's
`stats/summary` reports as `node.fs`/`runtime.imageFs`. In every one of those reps, the
sampled `node_diskpressure` condition read **`False` throughout**, even at the moment of
active EIO/ENOSPC storms (P0.1: 8 real ENOSPC errors during the sampling window, node
DiskPressure never flipped; P0.5: pressure levels up to 90% pre-fill, EIO counts up to 837,
corrupted-file fractions up to 264/280 — DiskPressure never observed True in any of the ten
reps' final `kubectl get nodes` snapshots).

This is itself the load-bearing half of P2.2's question: on a **dedicated** cache volume
(the deployment pattern this whole article argues operators should use, precisely *because*
the shared-fs alternative ties lazy-pull failure to eviction timing in ways that are hard to
reason about), kubelet's node-pressure eviction machinery is **structurally blind** to the
volume where the actual failure is happening — it isn't a race that eviction sometimes loses,
it's a filesystem kubelet was never watching in the first place. The article's own dedicated-
volume recommendation is therefore not just a workaround for ENOSPC risk, it's also *why*
node-level eviction can't help: separating the cache from `imageFs` is what makes the
dedicated-volume pattern safe from a different angle than intended (isolating capacity
planning) — it also means kubelet has zero signal, positive or negative, about that volume's
state, for better (no OOM/eviction interference during a legitimate cache fill) or worse (no
automatic mitigation of the P0.1-P0.5 failure modes either).

## What remains a genuinely open question

Whether a **shared-fs** topology's DiskPressure eviction would actually win the race against
eStargz's ENOSPC-induced corruption (evicting/GCing images fast enough to keep the FUSE
mount from ever hitting real ENOSPC) is *not* answered by the evidence above — it's a
distinct question requiring the live measurement this note is deferring. Flagged explicitly
as future work, not silently dropped: a follow-up run on a **fresh, single-purpose node**
(not one carrying this run's already-live system pods under the same snapshotter) could set
`root` in stargz's config to a path under the node's own `imageFs`-tracked filesystem from
cluster-creation time (avoiding any live daemon/root switch entirely) and repeat P0.1's
induction protocol there.
